Filesystem guide

What is a TeslaCam Sentry clip?

It is not one video file. It is a timestamped event directory containing short, synchronized camera segments plus optional event metadata and a thumbnail.

Scope. Tesla does not publish a stable machine-readable filesystem specification. This page separates behavior documented by Tesla from file details observed by the project. Camera count and metadata can vary with vehicle hardware, market, and firmware.

The recording volume

A vehicle-formatted recording drive uses exFAT and contains a top-level TeslaCam directory. Tesla documents three principal clip collections:

/
└── TeslaCam/
    ├── RecentClips/
    ├── SavedClips/
    └── SentryClips/
DirectoryMeaningLifecycle
RecentClipsContinuous rolling Dashcam footage.Up to roughly 60 minutes; old footage is overwritten.
SavedClipsFootage explicitly saved by Dashcam actions such as manual save, honk, or automatic safety event.Retained until deleted or storage management requires intervention.
SentryClipsFootage retained for Sentry Mode security events.Older events can be deleted by the vehicle when space is needed.

Some newer configurations can also contain EncryptedClips. This project does not currently parse or ingest encrypted recordings.

A Sentry event directory

Each observed event is represented by a directory whose name is a local wall-clock timestamp:

TeslaCam/SentryClips/2026-07-11_14-32-08/

The directory name follows YYYY-MM-DD_HH-MM-SS. It identifies the saved event, but should not be treated as a globally unique ID: clocks can change, time zones can change, and two devices can generate the same name.

Representative four-camera event

TeslaCam/SentryClips/2026-07-11_14-32-08/
├── 2026-07-11_14-23-00-front.mp4
├── 2026-07-11_14-23-00-back.mp4
├── 2026-07-11_14-23-00-left_repeater.mp4
├── 2026-07-11_14-23-00-right_repeater.mp4
├── 2026-07-11_14-24-00-front.mp4
├── 2026-07-11_14-24-00-back.mp4
├── … additional minute/camera segments …
├── 2026-07-11_14-33-00-right_repeater.mp4
├── event.json
└── thumb.png

The MP4 filename timestamp describes the segment start. The final suffix identifies the camera stream. Files sharing a timestamp are parallel views of approximately the same recording interval.

Video segments

TeslaCam footage is divided into short MP4 segments, commonly about one minute each. A saved event is therefore a time series of files per camera rather than a single movie.

<segment-start>-<camera>.mp4

2026-07-11_14-32-00-front.mp4
└────── timestamp ──────┘ └camera┘
Observed suffixViewCurrent project handling
frontForward-facing cameraSupported
backRear-facing cameraSupported
left_repeaterLeft side repeaterSupported
right_repeaterRight side repeaterSupported
Additional pillar streamsLeft and right pillar cameras on supported newer vehiclesNot modeled by the simulator yet
Do not assume exactly four files per timestamp. Tesla’s current manuals state that supported vehicles may save six videos per recording. Readers should discover camera suffixes rather than reject unfamiliar ones.

event.json

Observed Sentry event directories can include a small JSON document describing the trigger. A representative file used by this project is:

{
  "timestamp": "2026-07-11T14:32:08",
  "city": "Toronto",
  "est_lat": "43.65",
  "est_lon": "-79.38",
  "reason": "sentry_aware_object_detection",
  "camera": "5"
}
FieldInterpretationReliability
timestampEvent trigger time in local wall-clock form.Useful for choosing the trigger-minute segment; timezone is not encoded.
cityApproximate place label.Optional; should not identify an event.
est_lat, est_lonEstimated location, often encoded as strings.Optional and privacy-sensitive.
reasonMachine-readable trigger category.Values can evolve with firmware.
cameraNumeric trigger-camera code.Not the same vocabulary as filename suffixes.

The current server maps codes 3/5 to the left repeater, 4/6 to the right repeater, 7 to the rear, and other or unknown codes to the front. That is a project fallback policy, not a complete Tesla schema.

event.json is metadata, not a commit marker. Its presence does not prove that every video has finished writing, and its absence should not make otherwise valid video undiscoverable.

thumb.png

An event can also contain a thumbnail used for quick visual identification. It is supporting media, not evidence that the event directory is complete.

How the files appear over time

The filesystem is live while the vehicle owns and writes the volume. A reader may observe partially updated metadata and growing files:

RecentClips minute files open and grow
                 │
                 ▼
       Sentry trigger occurs
                 │
                 ├── event directory appears
                 ├── recent pre-trigger segments are copied
                 ├── event.json may appear
                 ├── thumb.png may appear
                 └── post-trigger segment(s) continue arriving
                                  │
                                  ▼
                    all observed files eventually stabilize

Directory-entry metadata can temporarily be inconsistent during a write. exFAT also distinguishes allocated length from Valid Data Length; bytes beyond the latter are not yet valid file content. This project’s live reader skips checksum-invalid entry sets and never reads beyond Valid Data Length.

There is no documented filesystem-level transaction that atomically declares an event complete. Completion must therefore be inferred locally from stable files and elapsed post-trigger time, then represented explicitly in the project’s higher-level ingestion protocol.

What our simulator models

The development simulator deliberately models a conservative, known subset:

  • One-minute segments for front, back, left_repeater, and right_repeater.
  • A rolling RecentClips buffer with oldest-first deletion.
  • A Sentry directory containing up to nine finished pre-trigger minutes and one post-trigger minute.
  • event.json and thumb.png.
  • Chunked writes without explicit sync, including interruption during an open segment.

It does not yet model six-camera layouts, encrypted clips, every trigger reason, firmware-specific metadata, or real H.264 byte structure. Simulator output is test data, not a canonical Tesla format.
