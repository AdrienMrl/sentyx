Overview TeslaCam filesystem Ingestion API
API v1

Upload events, not filesystem paths.

The agent converts Tesla’s live, eventually consistent directory into verified blobs and a versioned logical-event manifest. The server validates delivery and analyzes only explicitly finalized generations.

Protocol overview

stable TeslaCam file
        │
        ├── calculate SHA-256
        ├── PUT event metadata
        ├── PUT content-addressed blob
        └── add typed artifact to local event
                         │
                  local settle delay
                         │
                         ├── PUT manifest generation
                         └── POST generation/finalize
                                      │
                                      ▼
                              durable analysis job

The API does not expose TeslaCam/SentryClips as its resource model. Source paths are retained only as artifact provenance.

Endpoints

MethodEndpointPurpose
PUT/v1/events/{event_key}Idempotently create or enrich a logical event.
GET/v1/events/{event_key}Inspect state, current generation, artifacts, and analysis.
PUT/v1/blobs/{sha256}Store bytes under their verified content hash.
PUT/v1/events/{event_key}/manifests/{generation}Declare the typed artifacts in one event generation.
POST/v1/events/{event_key}/manifests/{generation}/finalizeVerify the generation and make it analysis-ready.

All endpoints except GET /healthz use the server’s existing bearer-token authentication when configured.

Event identity

The agent creates a deterministic key:

<device-id>:<source-directory-name>

pi-garage-01:2026-07-11_14-32-08

The source timestamp alone is not globally unique. Prefixing it with a stable device ID makes agent retries and restarts converge on the same server event.

1. Upsert the event

PUT /v1/events/pi-garage-01:2026-07-11_14-32-08
Content-Type: application/json

{
  "device_id": "pi-garage-01",
  "source": {
    "type": "tesla_sentry",
    "directory_name": "2026-07-11_14-32-08"
  },
  "detected_at": "2026-07-11T18:32:10Z",
  "trigger": {
    "occurred_at_local": "2026-07-11T14:32:08",
    "camera_code": "5",
    "reason": "sentry_aware_object_detection"
  },
  "location": {
    "city": "Toronto",
    "estimated_latitude": 43.65,
    "estimated_longitude": -79.38
  }
}

trigger and location are optional. They are populated when a valid event.json becomes available; that file is enrichment, never a completion marker.

{
  "id": "pi-garage-01:2026-07-11_14-32-08",
  "state": "receiving",
  "generation": 0
}

2. Upload verified blobs

PUT /v1/blobs/67d2a1…
Content-Type: video/mp4
Content-Length: 28123904

<raw MP4 bytes>

The server streams the body into a temporary file while calculating SHA-256. It rejects a mismatch with 422 Unprocessable Entity, then atomically moves valid bytes into:

data/blobs/67/67d2a1…

Uploading an existing hash is idempotent. This makes retries cheap and prevents duplicate storage when content is referenced more than once.

3. Publish a manifest generation

PUT /v1/events/{event_key}/manifests/1
Content-Type: application/json

{
  "generation": 1,
  "observed_through": "2026-07-11T18:34:20Z",
  "artifacts": [
    {
      "id": "2026-07-11_14-32-00-front.mp4",
      "kind": "video",
      "sha256": "67d2a1…",
      "size": 28123904,
      "media_type": "video/mp4",
      "source_name": "2026-07-11_14-32-00-front.mp4",
      "segment": {
        "started_at_local": "2026-07-11T14:32:00",
        "camera": "front"
      }
    }
  ]
}

Camera is an open string rather than a closed enum. Unknown future streams can pass through without a protocol upgrade.

If referenced content is absent or has the wrong size, the response identifies it:

{
  "generation": 1,
  "status": "incomplete",
  "missing_blobs": ["67d2a1…"]
}

4. Finalize explicitly

POST /v1/events/{event_key}/manifests/1/finalize
Content-Type: application/json

{
  "completion_reason": "post_trigger_window_settled",
  "settled_at": "2026-07-11T18:34:32Z"
}

Finalization succeeds only if the manifest exists and every artifact resolves to a verified blob of the declared size. Success moves the event to ready and atomically inserts a durable analysis job.

{
  "event_id": "pi-garage-01:2026-07-11_14-32-08",
  "generation": 1,
  "status": "ready"
}

Agent completion rule

The agent starts or resets its settle timer whenever another stable artifact uploads successfully. The default is 90 seconds and is configurable with -event-settle.

event directory discovered
          │
          ├── stable files upload as they appear
          ├── growing files remain local
          ├── event.json is optional metadata
          └── no newly stable file for settle delay
                              │
                              ▼
                        finalize generation
The timer is a local filesystem heuristic. Unlike the old design, the server does not mistake network silence for proof that Tesla finished writing.

Late artifacts and generations

If another file stabilizes after generation 1 was finalized, the agent uploads it and publishes generation 2 containing the complete artifact set. Older generations remain an audit trail.

generation 1 ready
        │
        └── late segment arrives
                    │
                    ├── upload blob
                    ├── manifest generation 2
                    └── finalize generation 2

A generation older than the server’s current generation is rejected with 409 Conflict.

Durable analysis jobs

Finalization and job creation occur in one SQLite transaction. One serialized worker claims pending jobs, marks them running, and records completion or failure. Jobs left running by a process crash are reclaimed at startup.

receiving → ready → analyzing → done
                         │
                         └──────→ failed

Analyzer failures receive up to three durable attempts with bounded backoff. Each job is keyed by (event_id, generation), so a late generation can be analyzed independently.

Compatibility and current limitations

  • The legacy PUT /files/TeslaCam/SentryClips/… endpoint remains available during migration.
  • The Pi agent and teslcam-watch now publish through API v1 when -post-to is enabled.
  • Finalized manifests are materialized into the existing file metadata view, so the current single-clip Gemini analyzer keeps working.
  • The analyzer still selects one trigger-relevant clip. Passing the complete event manifest to a multi-camera analyzer is the next analysis-layer change.
  • The agent’s queue is recoverable from its local spool and a fresh filesystem scan, but it is not yet a separately persisted outbox.
  • Uploads restart from byte zero after interruption; HTTP range-based resume is not implemented yet.
